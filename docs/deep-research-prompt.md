# Tindalos 深度功能研究提示词

## 提示词正文

请对我的个人项目 https://github.com/SgtBaixiao/tindalos 做一次面向实际主持的深度功能设计研究。目标是让 KP 能可靠地依据模组备团、应对玩家行动，并在下一场延续真实发生的状态。聚焦一个连续用例：调查型克苏鲁模组的原文阅读、备团、实际游玩和续团。用这个用例检验现有能力，保持当前产品范围。

先从原始证据建立理解。固定一个仓库提交，直接审阅领域模型、生成与修订流程、记忆写入、评测和前端数据调用；读取未经摘要的模组正文、地图、人物资料和规则出处，保留页码。若能获得实际游玩材料，读取逐字稿、玩家行动、检定结果、KP 裁定和会后记录。缺失的材料明确列出；可用公开官方模组建立方法样例，但不得据此声称已验证我的实际使用需求。

请完成以下工作：

1. 找出当前不合理的设计。每项都说明具体触发、源码证据、对 KP 或玩家的影响，并尽量用最小反例复现。重点核对：生成计划与已发生事实是否混淆，连线是否代表有意义的选择，NPC 人格是否影响行为，原文忠实度是否误判，编辑和记忆是否指向正确的剧本版本。
2. 重建一个模组的调查与状态模型。标注玩家需要得出的结论、支持结论的线索、获得条件、替代路线、NPC 动机和未解决问题。分别记录世界事实、KP 掌握的信息、NPC 的知识和玩家已知信息；区分原文事实、模型创作建议、实际游玩记录与 KP 的明确裁定。
3. 对照第一手设计方法深入研究。阅读 Chaosium 官方材料、Justin Alexander 的线索与情境准备原文、Pelgrane Press 的调查型游戏设计材料，并结合 Agent 评测和记忆研究的原论文、官方文档。比较适用条件与冲突，说明哪些结论是来源直接支持的，哪些是对 Tindalos 的设计推断。
4. 从发现中选择最多两个最值得深化的功能。每个方案明确用户触发、输入证据、状态变化、输出形式、人工确认点、失败行为和取舍。给出能具体讨论的案例或小型原型规格，解释它如何改善同一个备团和续团用例。
5. 提供能够推翻方案的验证方法。用线索遗漏、检定失败、玩家改变顺序、NPC 死亡、错误记忆、局部修订等变形或故障案例，检查结论可达性、状态一致性和信息泄露。把相互矛盾的声明、证据不足的问题和未发生事件作为负例，要求系统区分支持、矛盾与未知。
6. 设计独立验收。用带页码的原文建立人工复核基准，用可重放场次记录建立实际状态基准；让未参与设计的 KP 进行盲评或对照试用。记录查找规则与线索的耗时、遗漏和错误裁定、处理偏离所需的补充准备、续团事实错误，以及对应证据。测试通过、LLM 分数和访谈意见各自说明了什么，需要分别解释。没有实际试用就只提交验证计划，不编造成绩或访谈。

最后交付：有来源的项目问题审查、同一个模组的领域与状态示例、两项功能的具体设计及取舍、独立验证计划，以及优先级。先用业务对象和证据约束方案，再根据执行与数据需求讨论工程架构，说明现有技术哪些仍适合、哪些需要改变。每个架构建议都应能追溯到具体功能要求和失败案例。

中文文档先使用 `doc-writing` 定主题与框架，由 `de-ai-tech-writing` 主导技术论证，成稿后显式使用 `haohao-shuohua` 清洗并运行机械扫描。保留事实、命令、术语和证据，不补造用户需求。

## 改写依据

专业工作增加的是对真实主持行为的分析和独立检验。原始材料包括仓库源码、完整模组及规则、实际玩家行动和 KP 裁定，避免只以 README、生成摘要和既有评分定义需求。

方法包括源码契约走读与最小反例、线索与结论标注、事件风暴与知识状态机、变形测试和故障注入，以及独立 KP 对照试用。工具可采用 PDF 页码与标注、SQLite 与 JSONL 记录、NetworkX 图分析、pytest、Vitest 和浏览器操作记录；工具按证据需要选用。

结果的外部判据是原文可以逐页复核，实际状态能从场次记录重放，失败与矛盾案例能被正确识别，独立 KP 可以完成同一备团任务并指出仍然不可用的地方。
