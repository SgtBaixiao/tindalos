# Tindalos 重构前的功能判断与验证方案

Tindalos 已有结构化剧本、资料检索、生成编排、编辑、评测和记忆的工程基础。下一次重构最需要解决的是这些能力如何支持同一场调查：KP 依据什么准备，玩家如何取得信息，行动改变了什么，下次应从哪个真实状态继续。建议先深化两项能力：解释线索的调查用途，以及保存有来源、有知情范围的世界与游玩状态。

这份报告供维护者确定功能约束后讨论架构。审查固定在提交 `feca892bfbaf7b7a9ca04dc87b2908ad03d7fc9f`，日期为 2026-11-19。现有行为来自源码与局部验证；游戏设计依据来自官方规则及作者原文；新功能和验收门槛均为本次研究建议，尚未经过实际主持验证。

## 项目的目标与当前差距

我的理解是：Tindalos 面向人类守秘人（KP），把模组与规则资料转成可编辑、可检查、可续用的备团材料。Campaign、Act、Scene、Event、NPC、Clue 是主要业务对象。工作台、模组库、规则问答、历史回看、评测和记忆服务这一用途。项目也承担 Agent 工程实践目标，强调可测试、可观察和降级。

现有对象适合组织输出，却不足以完整表达调查过程。一个事件在剧本里存在，不能说明它已经发生；一个图节点可达，不能说明玩家知道入口或满足获取条件；一段 NPC 描述存在，不能说明其动机影响了行动。这些差距应成为重构的输入。

| 优先问题 | 代码证据与具体触发 | 对主持的影响 |
|---|---|---|
| 计划与已发生事实混在记忆中 | [生成后的捕获](../src/tindalos/pipeline.py#L418)把剧本事件写入[情景记忆](../src/tindalos/memory_entries.py#L194)；实际回叙另存于[场次表](../src/tindalos/memory_entries.py#L887)，整合与续写检索读取记忆条目 | 系统已有机制容易把计划作为回忆上下文，而本场真实变化尚未进入同一续写路径；尚未实测模型是否因此作出错误续写 |
| 线索缺少调查含义 | [Clue 模型](../src/tindalos/models.py#L59)只有描述和对象引用；[装配器](../src/tindalos/pipeline.py#L442)每幕放一条通用线索，关联第一场景的最后事件 | 无法说明信息支持什么结论，或漏检、误读、改变顺序后还有哪些路径 |
| 评测会奖励无意义的结构 | [场景处理](../src/tindalos/pipeline.py#L198)添加通往后续事件的边；[忠实度判据](../src/tindalos/eval_/runner.py#L197)使用检索分数与词元重叠；[人工 KP 层](../src/tindalos/eval_/runner.py#L416)固定跳过 | 分支数和原文支持率不能据此代表实际可选路线或事实正确 |
| 人格还未成为行为依据 | [NPC 模型](../src/tindalos/models.py#L46)缺少明确动机、知识和资源；[场景生成](../src/tindalos/pipeline.py#L352)收到 NPC ID，而非刚生成的人格对象 | 玩家绕路、拖延或公开指控时，系统缺少解释 NPC 反应的状态约束 |
| 使用过程与保存未接通 | [生成按钮](../frontend/src/components/ProgressBand.tsx#L60)缺省走模板；结束只更新剧本 ID；[手动保存](../frontend/src/components/NodeDrawer.tsx#L57)只更新浏览器状态；资料库没有直接进入生成的选择流程 | KP 不能可靠完成“选模组→生成→修改→重新打开→续团” |
| 模组、剧本版本与场次身份未分开 | [剧本 ID](../src/tindalos/pipeline.py#L104)由文本派生；[历史注册](../src/tindalos/history.py#L212)覆盖同 ID 快照；[CLI](../src/tindalos/cli.py#L126)另走生成循环 | 重复生成、局部修改与场次记录可能无法指向可复核的版本；两个生成入口还需分别保持行为一致 |

本轮隔离运行原函数，观察到两个最小反例：原本线性的三个事件被添加出边，满足数量型分支条件；声明“霍普已经死亡。”与给定片段“霍普还活着。”共享姓名，因此被原支持判据接受。输入是人工构造，检查范围止于提取出的原函数，未运行完整生成或检索流程。具体观察保存在 [research-probes.json](research-probes.json)。

## 专业研究应从原始主持过程开始

资深调查型游戏设计师会先还原幕后因果与信息获取，再观察 KP 怎样查找、裁定和处理偏离。Agent 工程师随后核对系统是否保持这些约束，并建立能揭示错误的评测。两者需要共同定义“可主持”的含义。

起点应是未经摘要的模组正文、地图、证词、手册材料、规则及页码，以及实际场次中的玩家行动、检定、KP 裁定与时间戳。源码也是原始材料，README 和已有评分只提供待核对的声明。仓库的《雾港之夜》只是短前提，不能代替完整模组或实际游玩记录。

方法与工具应服务这些证据：用 PDF 阅读器核对页码和标注；用线索与结论表还原推理，用带条件的图检查调查路径；用事件风暴和状态机梳理“尝试、裁定、已发生”；用 pytest、Vitest 与浏览器记录验证接口和编辑保存；用 SQLite 快照及 JSONL 调用记录重放状态，用变形测试和故障注入暴露续团错误。NetworkX 可以检查关系与依赖，普通图可达性仍需补充状态条件。工具名称不构成架构选型结论。

独立依据应来自原文页码、可重放场次记录，以及未参与开发的 KP。程序测试确认约束；模型评分帮助查找可疑内容；实际主持确认材料是否可用。三种证据分别报告。

## 设计依据及其适用边界

[Three Clue Rule](https://thealexandrian.net/wordpress/1118/roleplaying-games/three-clue-rule)建议为目标结论准备多条线索；[Don’t Prep Plots](https://thealexandrian.net/wordpress/4147/roleplaying-games/dont-prep-plots)建议准备局势、对手目标和未受干预时的行动。这些是作者的设计方法，缺少本轮可复查的对照实验，不能据此保证调查不会停滞。

Pelgrane 的 [Clues vs. Leads](https://pelgranepress.com/2020/02/21/clues-vs-leads/)区分引向场景的信息和帮助解释真相的信息。[GUMSHOE SRD](https://pelgranepress.com/gumshoe/files/GUMSHOE%20SRD%20CC%20version.pdf)提出从幕后事件推导证据，必要信息在符合条件时不由掷骰决定。但这项获取规则属于 GUMSHOE。CoC 的失败、重试和孤注一掷应依据 [Chaosium 官方 Quick-Start](https://www.chaosium.com/content/FreePDFs/CoC/CHA23131%20Call%20of%20Cthulhu%207th%20Edition%20Quick-Start%20Rules.pdf)及选定模组保留，新增替代方法交由 KP 采用。

Agent 评测研究要求区分运行过程、结果与证据；[LongMemEval](https://arxiv.org/pdf/2410.10813)提供知识更新、时间推理与证据检索的测量方法。[LangGraph 持久化](https://docs.langchain.com/oss/python/langgraph/persistence)和[中断恢复](https://docs.langchain.com/oss/python/langgraph/interrupts)提供执行机制，不能自动决定哪些记忆是真的。本项目的知情权限、事件确认和修订约定需要另行定义。

游戏来源的阅读范围与分歧见 [research-investigation-design.md](research-investigation-design.md)；评测与记忆方法见 [research-validation-methods.md](research-validation-methods.md)。官方 PDF 的引用页码来自检索提供的正文，尚未逐页图像核验；正式建立评测基准前需冻结下载件并复核。

## 第一项深化：线索应说明推理用途与获取机会

用户触发是 KP 备团或处理偏离时询问：“这条线索有什么用？玩家没拿到它会怎样？”输入为具体模组版本、原文证据、目标结论、调查入口及当前已知信息。输出以简短调查表为主，图用于辅助浏览。

| 必需信息 | 需要表达的含义 |
|---|---|
| 结论及依据 | 信息只能提示继续调查，还是足以支持一个判断；需要其他前提吗；有哪些反证 |
| 获取条件 | 所在地点、知情 NPC、可行行动、规则条件、时间与资源；哪些入口对玩家可见 |
| 失败与替代 | 失败代价、重试条件、其他原文路径，以及尚未解决的阻断缺口 |
| 来源与状态 | 模组页码或文本行、原文是否确定、KP 是否批准补写、谁已获得信息 |

检查要同时处理“任一依据可支持”和“多个前提缺一不可”。三条线索都依赖同一 NPC 开口，仍共享一个失败点；改写同一段证词也不增加取得机会。程序可检查条件依赖，KP 负责判断证据是否足以支撑推理，以及玩家提出的其他调查方法是否合理。

在仓库[短前提](../examples/sample-module.md#L3)中，霍普声称灯塔传来怪声，这能支持“灯塔值得调查”；它尚不能证明声音来自神话生物。乔纳斯归来是镇上流言，日志中的句子是文件记载。补写目击者或其他调查路径时，界面应显示创作建议及其用途，KP 采纳后才进入剧本版本，随后仍需检查一致性。

功能不替玩家宣布真相，也不自动把漏掉的线索移到下一场。玩家放弃调查、承担失败或错过机会都可以成为合理结果。工具应揭示条件和缺口，让 KP 作出有依据的选择。代价是需要做较细的来源与条件标注；可先标注关键结论，避免把每句描写都结构化。

## 第二项深化：续团应依据已确认事件与知情范围

用户触发是记录场次、修改设定、处理 NPC 反应或开始续团。输入为采用中的剧本版本、原始场次材料和 KP 裁定。模型可提取候选变化，KP 确认后再更新实际状态。

需要区分内容的来源与状态：原文设定、模型建议、KP 已采纳的改编、实际发生事件和显式纠正。另记录谁说了这句话、谁知道什么、何时有效。原文明确写“有人声称”时，确定的是该说法存在，内容真伪可以保持未定。NPC 和玩家的知识也不能直接等同于世界真相。

最小流程是“场次原始记录→候选事实变化→KP 确认→已确认事件→当前状态及续团摘要”。摘要与检索是派生内容，必须能定位到确认事件和原始材料。待确认或冲突项保持可见；写入失败后不得显示保存成功。纠正旧裁定须保留纠正依据和受影响状态，不能用最近生成的摘要悄悄覆盖。

以下是人工构造的场次规格，用于讨论行为，未发生实际游玩。

| 同一调查中的内容 | 系统应保存的状态 |
|---|---|
| 备团计划让霍普交出日志 | 尚未发生，玩家未因此获得内容 |
| 实际记录显示玩家跳过霍普，先到灯塔 | 已确认路线与当前位置；日志内容仍未交付 |
| 玩家 A 单独看到一份文件，尚未转述 | A 已知；其他玩家未知；NPC 的知识另行判断 |
| 后来发生原文设定之外的 NPC 死亡 | 作为本战役已确认变化，保留时间与裁定；原始模组仍可查 |
| 模型为续团写“全队已经读过日志” | 与当前知识状态矛盾，不能写入事实 |

NPC 的动机、知识、资源和条件反应可作为这一状态功能的一部分。玩家拖延后，系统根据已采纳设定提出 NPC 会尝试的行动及可观察后果；提议先由 KP 裁定，不能凭人格标签替 NPC 获得未接触的信息。只建模影响当前调查的少量状态，不需要先做自动主持或全世界模拟。

## 用同一个连续用例检验两项设计

正式验证选一个固定完整模组，冻结 PDF 哈希、剧本版本、提示词、模型与生成配置。可以先用公开《The Haunting》建立方法样例，但用户实际使用的模组和场次记录尚未取得。

| 验证层 | 方法与独立依据 | 会推翻方案的结果 |
|---|---|---|
| 原文与推理 | 独立 KP 先标注关键事实、结论、获取条件和未定事项，再逐项核对输出及页码 | 关键事实矛盾、人物说法被当作真相、无依据补写冒充原文，或遗漏必要条件 |
| 路径与裁定 | 从冻结状态注入漏检、改变顺序、NPC 死亡及玩家另提方法；复核承诺路线的可见性、条件和区别后果 | 所谓替代入口共用不可解除的障碍，依赖玩家未知秘密，或总被强制带回同一结果 |
| 续团与知识 | 对同一证据分别运行实际检索与人工提供全部必要证据的对照；核对未发生、已更新与未知问题 | 计划变成经历、角色秘密越权、显式裁定被低权威推断覆盖，或无法区分漏检与读错 |
| 保存与恢复 | 在独立存储副本上注入写失败、超时、中断和重复提交，另用特殊事实检查战役隔离 | 已确认事件丢失或重复、跨战役混入，或前端显示成功而实际未保存 |
| 实际主持 | 未参与设计的 KP 使用匿名材料完成同一任务，保留查找时间、回翻原文次数、遗漏、补充准备与错误裁定记录 | 关键问题仍无法仅凭材料裁定，或出现新的事实和知识错误 |

计划中的故障情境应分别从相同副本恢复并保留全部运行结果。变形测试可用同义改写、无关记录和单项裁定变更；前两者不应改变关键状态，后一项只应影响依赖它的内容。关键可靠性错误逐条报告，并明确各指标分母。效率是否改善需要实际基线与足够样本，当前不设没有依据的提升比例。

同一个谜题由同一组参与者重复游玩会有记忆偏差。材料走查可以做匿名对照；实际游玩的收益比较需独立组或适当匹配的情境，并说明样本与顺序影响。一次场次能暴露错误，不能证明总体可靠率。

## 功能约束怎样影响工程架构

建议先明确模组版本、战役、剧本修订、场次与评测运行的独立身份。生成、手动修改和回叙都应写入同一组领域约束；浏览器、CLI 与网页服务使用共同的业务入口。前端显示采用中的版本与保存结果，评测绑定输入证据和具体修订。

来源记录、确认事件和当前状态应有明确的持久化边界，必要写入要保持一致并可恢复。先用普通事务和可追溯记录兑现这些要求；是否需要完整事件溯源，要由恢复和修订需求决定。向量索引与摘要可重建，不能成为事实的唯一来源。

现有 Pydantic、LangGraph、React Flow、SQLite 和检索组合仍可承担不少工作。需要调整的是对象语义、共同服务入口、写入确认及评测标准。运行编排能恢复不等于事实正确，模型分支并行也不等于 NPC 有自主行为。先证明这个连续用例成立，再用真实负载判断存储和部署是否需要更换。
